# Rails 8.0系 → Rails 8.1系 段階移行

## 目的
Rails 8.0系で既存MVP機能の動作確認が完了している状態を前提に、Rails 8.1系へ段階移行し、TakuVault の既存MVP機能が Rails 8.1系上で壊れずに動作することを確認する。

本Issueでは、Rails 8.1系の新機能採用ではなく、既存構成・既存機能の維持を目的とする。

このIssueが green になった状態を、後続の「Rails 8.x framework defaults 段階適用」の前提条件とする。

## 背景
現在のTakuVaultは、Rails 8.0系 / Render Docker / ActiveStorage + Cloudflare R2 / Solid Queue / Devise / Pundit / Sprockets / tailwindcss-rails を前提に構成されている。

Rails 8.1系へ進むにあたり、Rails本体の更新と framework defaults 更新を混ぜると、不具合発生時の原因切り分けが難しくなる。

そのため、本Issueでは `config.load_defaults 7.2` を維持したまま Rails 8.1系へ上げ、既存MVP機能、R2永続化、Worker、purge_later、アップロード制限、認可境界が維持されていることを確認する。

前提Issue「Rails 7.2.3 → Rails 8.0系 動作確認」が完了していない場合、本Issueは BLOCKED とする。

## Verification
ローカルでは、Docker Compose環境を前提に最低限以下を確認する。

- `docker compose exec web bin/rails db:prepare`
- `docker compose exec web bin/rails db:migrate`
- `docker compose exec web bin/rails routes`
- `docker compose exec web bin/rails tailwindcss:build`
- `docker compose exec web bin/rspec`

ホスト側でRailsを直接実行できる環境が整っている場合のみ、上記の `docker compose exec web` を省略してよい。

production相当の assets:precompile を確認する。

- `RAILS_ENV=production SECRET_KEY_BASE_DUMMY=1 APP_HOST=localhost:3000 bundle exec rails assets:precompile`

production相当boot / env fail-fast は最低限以下を確認する。

- `APP_HOST` 不足時にfail-fastする
- R2系環境変数不足時にfail-fastする
- 必須envを揃えた場合、production相当bootが通る

preview環境では最低限、以下を確認する。

- Web Service が起動する
- Worker Service が起動する
- アップロード → 一覧 → 詳細 → Session詳細 → Where used → 削除 → 再参照不能が成立する
- 再デプロイ後もR2上の添付を参照できる
- `purge_later` / `analyze` / `variant(transform)` が滞留しない
- 不許可形式・サイズ超過がサーバ側で拒否される
- 他人のAsset URL直打ちが通らない
