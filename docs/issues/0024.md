# Issue #24: (19) Asset削除整合性

- State: OPEN
- UpdatedAt: 2026-03-10T06:23:45Z

## Body

## 目的（このIssueで達成する価値）
素材（Asset）を削除したときに、関連するUsageと添付ファイルが一貫して削除され、DB整合性と所有権安全性が崩れないようにする。

---

## スコープ

### 含む
- **Asset削除の仕様を固定する**
  - Asset削除 → （DBにより）関連Usage削除 → 添付ファイル `purge_later`（ActiveStorage）
- **認可**
  - Asset削除は Pundit `authorize` により **所有者のみ** 実行可能（URL直打ち含む）
- **削除整合性（DB/ARの方針を混在させない）**
  - **推奨：DBを正本に寄せる**
    - `usages.asset_id -> assets.id` を **ON DELETE CASCADE** にする（Usage残存を構造的に防止）
  - ActiveStorage側はDB CASCADEの対象にしない（ActiveStorageの仕組みに委譲し、`purge_later` で物理削除する）
- **失敗時の整合性**
  - `purge_later` は非同期のため、レコード削除後も blob が即時消えないことは許容
  - ただし **Usage が残る／他ユーザーが参照できる** 等の “参照整合性破壊” は許容しない
  - `purge_later` の完了確認は「ジョブが enqueue されたこと」＋「worker稼働時に最終的に消えること」で判断する（worker停止中に消えないのは仕様）
- **画面/UX**
  - Asset削除後は素材一覧へリダイレクトし、成功/失敗のフラッシュを表示する
  - 削除確認（confirm）を表示する（文言はMVP相当で簡潔に）

### 含まない
- Session削除/Scene削除/Tag削除の整合性（それぞれ別Issueの責務）
- 添付のウイルススキャン等（MVP外）
- 物理ストレージ（R2）上の残骸監査やガーベジ回収（将来）

## 受け入れ条件（Yes/No）
- [ ] 自分のAssetを削除すると、関連するUsageがすべて削除される（UsageがDBに残らない）
- [ ] 自分のAssetを削除すると、添付ファイルが `purge_later` で削除される（少なくとも enqueue を確認できる）
- [ ] 他ユーザーのAsset削除URL直打ちは拒否される（Punditで拒否 / fail-closed）
- [ ] Asset削除後、Where used（使用先）に参照切れが残らない（Usageが残存しない）
- [ ] 削除操作は二重送信により二重実行されても破綻しない
  - 2回目は `policy_scope(Asset).find(...)` で見つからず **404（RecordNotFound）等で安全に終わる** ことを許容
- [ ] 削除後は素材一覧へ戻り、成功/失敗が分かる

## DoD（完了条件）
- [ ] DB/ARの削除方針が一貫している（CASCADE or dependent を混在させない）
- [ ] Policy により所有権（destroy権限）が担保される
- [ ] 主要な失敗ケース（権限なし、既に削除済み、添付なし等）で例外が起きない
- [ ] **RSpec/System spec の新規整備はしない**（既存CIが要求する場合のみ最小限に留める）

## 失敗ケース（最低3つ）
- [ ] Assetは消えたがUsageが残り、画面で参照切れ／例外が起きる
- [ ] Usageは消えたが添付blobが残り続け、ストレージ肥大化する（worker停止等で purge が滞留）
- [ ] 認可漏れで他ユーザーのAssetが削除できてしまう

## 最小テスト/検証（手動を正本）

### Model/DB（手動確認）
- [ ] `usages.asset_id` に **ON DELETE CASCADE**（または同等の整合方針）があることを確認できる
- [ ] UNIQUE/FK制約違反が削除時に発生しない

### Policy（手動確認）
- [ ] `AssetPolicy#destroy?` が所有権で拒否できる
- [ ] `policy_scope(Asset)` 起点で他人のAssetが参照できない（結果として destroy 対象も取得できない）

### System（手動確認）
- [ ] 自分のAssetを削除すると、Assetが一覧から消える
- [ ] 削除後、そのAssetのUsageがDB上から消える（Where used に出ない）
- [ ] 他人のAsset削除は拒否される（URL直打ち含む）
- [ ] 削除を2回叩いても致命的に落ちない（404等で安全に終わる）

### Implementation constraints（必須）
- [ ] **AssetsController は `@asset.destroy` を使う（`delete` 禁止）**
  - 理由: `delete` はコールバックを通らず、ActiveStorage の `purge_later` が走らない可能性があるため。
- [ ] **添付の purge は ActiveStorage の dependent（破棄時）に委譲する**
  - `asset.file.purge_later` を **destroy 前に手動で呼ばない**（destroy 失敗時に purge だけ enqueue される等の逆流を防ぐ）。
- [ ] **`purge_later` の完了判定を固定**
  - 必須: purge job が **enqueue されたこと**を確認できること
  - 任意: worker 稼働時に最終的に blob/attachment が削除されること（環境依存）
- [ ] **権限不一致は fail-closed を優先**
  - URL直打ち含め、所有権不一致は **404 相当（RecordNotFound 等）を許容/推奨**（403固定にしない）。
- [ ] **DB CASCADE の対象を限定**
  - `usages.asset_id -> assets.id` の **ON DELETE CASCADE のみに限定**
  - ActiveStorage（`active_storage_attachments` / `active_storage_blobs`）は CASCADE 対象にしない。
- [ ] **FK 付け替え migration の安全策**
  - 既存FKがある前提で、`foreign_key_exists?` 等で存在確認してから drop/add する（migration 失敗を避ける）。
- [ ] **モデル関連を置く場合のルール（方針混在防止）**
  - `has_many :usages` を置くのは可
  - ただし **`dependent: :destroy` / `dependent: :delete_all` を付けない**（DB CASCADE と混在させない）。
- [ ] **二重実行（2回目）の期待値を固定**
  - 2回目は `policy_scope(Asset).find(params[:id])` が見つからず **RecordNotFound → 404** 等で安全に終了（余計な rescue/冪等化ロジックは追加しない）。

### 運用/検証の補足（推奨）
- [ ] **`structure.sql` 運用のため**、migration 実行後に structure dump が必要（差分が出る前提）。
- [ ] worker 停止時は purge が滞留し得るが、**Usage 残存や他ユーザー参照などの参照整合性破壊は許容しない**。
