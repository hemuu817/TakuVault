# Rails 7.2.3 → Rails 8.0系 動作確認

## 目的
Rails 7.2.3 から Rails 8.0系へ段階移行し、TakuVault の既存MVP機能が Rails 8.0系上で壊れずに動作することを確認する。

本Issueでは、Rails 8.0系の新機能採用ではなく、既存構成・既存機能の維持を目的とする。

このIssueが green になった状態を、後続の「Rails 8.0系 → Rails 8.1系 段階移行」の前提条件とする。

## 背景
現在のTakuVaultは、Rails 7.2.3 / Render Docker / ActiveStorage + Cloudflare R2 / Solid Queue / Devise / Pundit / Sprockets / tailwindcss-rails を前提に構成されている。

Rails 8系へ進むにあたり、まず Rails 8.0系で既存MVP機能が維持できることを確認する。

Rails 8.0新規アプリの標準構成を取り込むのではなく、既存構成を維持したまま Rails 8.0系へ上げる。

## 決定事項
- 対象バージョンは固定パッチではなく「実装時点の Rails 8.0系 最新安定パッチ」とする
- 本Issueでは `config.load_defaults 7.2` を維持する
- `config.load_defaults 8.0` への変更は後続Issueで扱う
- Rails 8標準構成への置換は行わない
- Devise / Pundit / Sprockets / ActiveStorage R2 / Solid Queue / Render Docker 構成を維持する
- Worker起動コマンド `bin/jobs start` を壊さない
- `bin/rails app:update` は必須タスクにしない
- RSpecは `bin/rspec` を使用する
- CIのRSpec実行コマンドが現状 `bundle exec rspec` の場合、`bin/rspec` へ寄せるかを確認し、変更する場合は `.github/workflows/ci.yml` のRSpec実行行のみを最小差分で変更する
- README / AGENTS.md の Rails 7.x 表記更新は本Issueでは原則行わず、Rails 8.1系移行が green になった後に最小更新する
- 動作に影響しない deprecation warning は記録し、後続Issueへ送る

## Verification
ローカルでは、Docker Compose環境を前提に最低限以下を確認する。

- `docker compose exec web bin/rails db:prepare`
- `docker compose exec web bin/rails db:migrate`
- `docker compose exec web bin/rails routes`
- `docker compose exec web bin/rails tailwindcss:build`
- `docker compose exec web bin/rspec`

ホスト側でRailsを直接実行できる環境が整っている場合のみ、上記の `docker compose exec web` を省略してよい。

production相当の assets:precompile を確認する。

- `RAILS_ENV=production SECRET_KEY_BASE_DUMMY=1 APP_HOST=localhost:3000 bundle exec rails assets:precompile`

production相当boot / env fail-fast は最低限以下を確認する。

- `APP_HOST` 不足時にfail-fastする
- R2系環境変数不足時にfail-fastする
- 必須envを揃えた場合、production相当bootが通る

preview環境では最低限、以下を確認する。

- Web Service が起動する
- Worker Service が起動する
- アップロード → 一覧 → 詳細 → 削除 → 再参照不能が成立する
- 再デプロイ後もR2上の添付を参照できる
- `purge_later` / `analyze` / `variant(transform)` が滞留しない
