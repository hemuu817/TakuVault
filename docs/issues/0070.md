# Post-MVP: フッターリンク（利用規約 / プライバシーポリシー / お問い合わせ / 使い方・FAQ / About）

## 目的（このIssueで達成する価値）
公開運用に必要な基本導線（法務・サポート・プロダクト説明）を整備し、どの画面からでもフッター経由で到達できる状態にする。

## 背景 / 課題
- MVPでは「Where used成立」「所有権認可」「DB整合性」「アップロード安全性」を優先するため、静的ページ群は後回しになっている。
- ただし、画面遷移図やREADMEの完成度、運用時の最低限の体裁として、Post-MVPでの実装方針をIssueとして明文化しておく必要がある。

## スコープ（やること）
### 1. フッターリンクの追加（共通レイアウト）
- フッターに以下のリンクを表示する（文言は暫定可）
  - About
  - 利用規約
  - プライバシーポリシー
  - お問い合わせ
  - 使い方 / FAQ
- ログイン前/ログイン後で表示方針を決めて統一する（原則は両方表示）

### 2. 静的ページの作成（DB不要）
- 以下の静的ページを追加する（本文は雛形でも可）
  - About
  - 利用規約
  - プライバシーポリシー
  - お問い合わせ
  - 使い方 / FAQ
- ルーティングを追加し、GETでアクセスできるようにする
- ナビゲーション（戻る/トップへ等）は最低限で可

## 非スコープ（やらない）
- 規約同意チェック、同意ログ、規約バージョン管理
- お問い合わせフォーム送信（ActionMailer等）
  - 代替案：mailtoリンク、Googleフォーム、GitHub Issue誘導など
- 多言語対応（i18n）

## 受入条件（Acceptance Criteria）
- [ ] フッターに上記5リンクが表示される（ログイン前後の方針も含めて統一されている）
- [ ] 各リンクから対応ページに遷移でき、HTTP 200で表示される
- [ ] 各ページのURLが固定で、リロードしても同じ内容が表示される
- [ ] フッターが主要画面（素材一覧/Session詳細/Asset詳細など）で共通表示される

## 仕様メモ
- ページ構成は `StaticPagesController` などで集約しても良い（views分割）
- レイアウトは `application.html.erb` に共通フッターとして実装する
- 公開時に文面を確定できていない場合は「雛形である」旨を明記してリスクを下げる

## テスト（推奨）
- System spec：
  - [ ] ルート（または任意の主要画面）からフッターリンクが表示される
  - [ ] 各リンクをクリックして対象ページが表示される
- Request spec（代替）：
  - [ ] 各静的ページが200を返す

## 依存関係
- 共通レイアウト（フッター表示）の導入・整理
- 主要画面のURL設計が確定していること（フッターの表示対象が確定していること）

## リスク / 代替案
- 法務文面が未確定のまま公開すると信用リスクがある
  - 代替：公開時点では「雛形」注記 + 外部フォーム/外部ページへ誘導
