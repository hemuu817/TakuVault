## 目的（このEpicで達成する価値）
本番環境で「アップロード→参照」が永続的に成立するストレージ構成と、アップロード上限方針（許可形式・サイズ等）を固定し、MVPのアップロード安全性を運用で継続できる状態にする。

## 前提（固定）
### 実行環境
- 本番は **Render（Docker）** で稼働する
- Renderのローカルディスクは揮発する前提のため、永続ストレージは外部（R2）に寄せる

### ストレージ
- ストレージは **Cloudflare R2（S3互換） + ActiveStorage** を採用する
- **ActiveStorage Direct Upload は使わない**（サーバ経由multipart固定）
- 参照は **認可済みAsset経由**でのみURL生成/表示する（blob直露出を避ける）
  - 署名URL共有リスクはMVPでは許容（将来プロキシ配信を検討）

### ジョブ基盤（queue_adapter / worker）
- ActiveJob を本番で確実に実行できるよう **queue_adapter と worker プロセスを用意する**
- queue_adapter は **DB-backed（Redis不要）**に固定する（推奨：Solid Queue）
  - worker は Render 上で **web とは別プロセス**として常時稼働させる
- `purge_later` / analyze 系ジョブが **worker により消化される**ことを前提とする
  - worker を置かない構成は採用しない（矛盾を残さない）

### DB運用
- schema_format は **structure.sql**（固定）
- queue 用テーブルを含め、migrate の結果が structure.sql に反映される運用を崩さない

## DoD（Epic完了条件）

- [ ] 本番/staging相当で ActiveStorage が R2 を使用して動作する
- [ ] アップロードした添付が、再デプロイ/再起動後も参照可能（揮発FSに依存しない）

- [ ] Render 上で **web と worker が別プロセスとして起動**できる（運用手順あり）
- [ ] staging相当で以下が成立する
  - [ ] 添付の analyze 系ジョブが滞留せずに実行される
  - [ ] `purge_later` による削除が滞留せずに完了する（残骸化しない）

- [ ] 拒否時の挙動（422等）と「中途半端が残らない」ことが整合している（Epic Dと矛盾しない）
