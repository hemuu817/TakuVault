# Tailwind CSS導入・ビルド基盤整備

## 目的（このIssueで達成する価値）

TakuVault で Tailwind CSS を利用できる状態にし、Rails / Docker / Render preview 環境で CSS ビルドと配信が成立することを確認する。

本Issueでは、Tailwind CSS の導入・生成物確認・assets pipeline 連携・production相当ビルド確認までを扱う。

既存ERB画面の本格的なUI調整は、後続の Tailwind retrofit Issue で扱う。

## 前提（環境固定）

- 本アプリの asset pipeline は **Sprockets**（sprockets-rails）である。
  - 根拠：`app/assets/config/manifest.js`（`//= link_*` 指令）と `config/initializers/assets.rb`（`config.assets.version` / `config.assets.prefix = "/static"`）が存在する。
  - Web上の Tailwind v4 記事の多くは Rails 8 = Propshaft 前提のため、そのまま当てはめない（Propshaft 固有の `stylesheet_link_tag :app`/`:all` 配信挙動などは本アプリの判断材料にしない）。
- `tailwindcss-rails` v4 系の入出力パス（v4で変更済み）
  - 入力CSS：`app/assets/tailwind/application.css`（v3 の `app/assets/stylesheets/application.tailwind.css` から変更）
  - 出力CSS：`app/assets/builds/tailwind.css`（アプリに読み込む実体）
- **Sprockets では出力 `app/assets/builds/tailwind.css` が pipeline に拾われる経路（manifest.js のリンク、または layout の stylesheet 参照）が成立していることを必ず検証する。** 現状の `manifest.js` には `../builds` のリンクが無いため、install 後に参照経路が成立しているかを確認し、不足していれば最小差分で補う。

## スコープ

**含む**

- `tailwindcss-rails` gem の追加
- `bin/rails tailwindcss:install` 相当の導入処理
- Tailwind 入力CSS（`app/assets/tailwind/application.css`）/ 出力CSS（`app/assets/builds/tailwind.css`）/ 関連生成物の確認
- Rails asset pipeline（Sprockets）経由で Tailwind 出力CSS が参照されることの確認
  - `manifest.js` のリンク有無、または layout の stylesheet 参照を確認し、不足分のみ最小差分で補う
- Docker内 development 環境で Tailwind クラスが反映されることの確認
- Docker内で `bin/rails tailwindcss:build` が成功することの確認
- Docker内で `bin/rails assets:precompile` が成功することの確認
- `assets:precompile` 実行時に Tailwind build が走ることの確認
- `bin/rails assets:precompile` 実行後、precompile由来の不要な成果物をコミット対象に含めていないことの確認
- Render preview（`RAILS_ENV=production`）へデプロイ後、実画面で Tailwind CSS が反映されることの確認
- Tailwind 反映確認のための最小限の view 差分

## 技術方針

- Tailwind CSS の導入は `tailwindcss-rails` gem に固定する
- `tailwindcss-rails` は v4系を前提にし、Gemfileでは major version を固定する
  - 例：`gem "tailwindcss-rails", "~> 4.0"`
- CLI実体は `tailwindcss-ruby`（`tailwindcss-rails` の浮動依存）が供給する。Node は不要。
  - Tailwind CSS 本体のバージョン固定が必要なら `tailwindcss-ruby` を pin する（任意）。本Issueでは `Gemfile.lock` での固定で足りるため pin は必須にしない。
- Node / npm / PostCSS パイプラインは採用しない
- CDN版 Tailwind は採用しない
- asset pipeline は Sprockets 前提とし、Sprockets 経由で Tailwind 出力CSS を配信する
  - 出力 `app/assets/builds/tailwind.css` が `manifest.js` または layout の stylesheet 参照で拾われることを検証する
- 生成ファイルのパスは、`bin/rails tailwindcss:install` 実行後の `git diff` で確認する
- 生成物が `tailwindcss-rails` README の現行仕様（v4）と矛盾しないことを確認する
- `tailwindcss:install` により `Procfile.dev` 等が生成された場合は差分を確認する
- 本Issueでは Docker開発環境の live reload / watch 常駐運用までは確定しない
- Tailwind反映確認は `bin/rails tailwindcss:build` による明示ビルドで行う
- 既存の `sassc-rails` は Tailwind と非互換（`SassC::SyntaxError` を誘発）。Gemfile に存在する場合は除去する（Rails 7.2 既定では未導入の想定）。

## Notes

- 本Issueは、Tailwind前提のUI実装へ移るための基盤Issueとして、現時点で優先して実施する
- 以後の新規ビュー実装・ビュー修正は Tailwind 前提で行う
- 本Issueでは Tailwind の導入確認に必要な最小限の view 差分のみ許可する
- 既存画面の見た目調整は、後続の Tailwind retrofit Issue で対象ファイルを列挙して扱う
- Devise画面のTailwind化は本Issueでは扱わない
- MVPでは Devise Recoverable / password系ルートを導入しない

- Rails実行モードとしての `RAILS_ENV=production` と、環境呼称としての preview を混同しない
- `tailwindcss:install` により `Procfile.dev` 等が生成された場合でも、本Issueでは watch常駐運用の確定までは扱わない
- `tailwindcss:build` は `assets:precompile` に自動アタッチされる（本番ビルドで自動的に出力CSSが生成される）。これは v4 仕様。
- `tailwindcss:build` は `test:prepare` にも自動アタッチされるが、発火するのは `bin/rails test` であり **`bin/rspec` では発火しない**。CSS 前提の spec がある場合は明示的に `tailwindcss:build` を実行する（本PJの spec 方針＝認可/主要導線中心であれば通常は不要）。
