# Issue #36: Epic G : 変換（MVP外）

## Body

## 目的
TakuVault内の「既存Asset」を対象に、各TRPGプラットフォームの容量制限（例：1MB / 2MB / 5MB）へ **確実に収める** ための「素材最適化（圧縮・軽量化）」機能群を **MVP外（Deferred）** として設計・仕様化する。

- 主目的：**最適化（容量削減）**
- 主目的から外す：フォーマット変換（例：mp4→APNG/MP3）
  - 変換が必要なら別Epic/別Issueへ分離する（本Epicのスコープ外）

---

## スコープ宣言（重要）
- 本Epicは **Deferred（MVP外）**。Phase 0/1（保管＋Where used最小成立）へ **混入させない**。
- MVP段階では最適化機能の露出を **確実に封印** する（Feature Gate 必須。後述）。

---

## 用語
- **最適化**：同一フォーマットのまま再圧縮・画質係数・色数削減・（動画像なら）FPS/間引き等により容量を下げる処理
- **変換**：フォーマット変更を含む処理（本Epicでは主目的にしない）
- **派生Asset**：最適化結果を上書きせず、新規Assetとして保存するもの
- **置換（容量回収）**：派生Assetへ参照を切り替え、元ファイルを削除して総容量を回収する操作（DB上書きはしない）

---

## 仕様方針（このEpicで固定する骨格）

### 1) Feature Gate（MVPから確実に隔離）
- `ENV["FEATURE_ASSET_OPTIMIZATION"]` 等で Gate を設ける
- Gate **OFF（MVP）** のときは必須（fail-closed）：
  - ルート非公開（または 404）
  - UIリンク非表示
  - Controller は fail-closed（404/403）
  - Policy でも deny（fail-closed）

### 2) 対象素材（既存Assetのみ / 静止画＋動画像）
- 対象：`png / jpeg / webp / gif / apng`
- **最適化対象は “既にTakuVaultにアップロード済みのAsset” のみ**
  - 最適化専用アップロード導線は作らない

### 3) 入出力フォーマット（変換しない）
- **入力と同形式に出力を固定**
  - `png→png, jpg→jpg, webp→webp, gif→gif, apng→apng`
- フォーマット変換はスコープ外（必要なら別Issue化）

### 4) プロファイル（プリセットは必達）
- プリセット：`<=1MB / <=2MB / <=5MB`（最終の定義・根拠は #37 で確定）
- **必達**：
  - 目標未達の場合は「失敗」として扱い、派生Assetを作らない
  - 失敗理由（未達・不正入力・処理タイムアウト等）を保存し、UI表示できる前提にする（記録方式は #38/#39 で確定）

### 5) カスタム最適化（許可するが、未達は失敗）
- カスタムは許可する方針
- 編集対象（暫定・最終確定は #37）：
  - 共通：色数（color_count）等
  - JPEG系：品質（quality）
  - 動画像：フレーム上限/間引き（max_frames）・FPS（fps）
- **カスタムでも最終的に目標サイズ未達は失敗**（曖昧挙動を採らない）

### 6) 上書き禁止（派生Assetとして新規作成）
- 最適化結果は **派生Assetとして新規作成**（監査性・安全性のため）
- 元Assetは保持し、派生関係を追跡できる設計とする（詳細は #39）
  - 例：`assets.derived_from_asset_id`

### 7) 置換（容量回収）オプション
- 最適化成功時は **必ず派生Assetを作成**（監査性）
- その上でユーザーに **置換（容量回収）** を選択させる
- 置換の要件：
  - DB上の “同一レコードのfile差し替え” はしない（上書き禁止）
  - 置換の実体は「参照の付け替え＋元ファイル削除」
    - Usage等の参照を派生Assetへ付け替え（例：`usages.asset_id` を派生へ）
    - 元Assetは “置換済み（superseded）” として保持し、通常一覧から除外できる前提（設計は #39）
    - 元ファイルは `purge_later`（ジョブ）で削除し容量回収（運用前提は #38）
- **置換しない** 場合：元＋派生が両方残るため、ユーザー総容量が増える（仕様として明示）

### 8) 同期処理禁止（必ず非同期）
- 最適化は重い処理になり得るため **必ずジョブ化**（#38）
- 連打・濫用・タイムアウト・失敗時の後片付けを前提に仕様化する

### 9) 濫用耐性（回数制限・同時実行制限・冪等性）
- **回数制限 / 同時実行制限** を前提にする（微調整で増殖しやすいため）
- 冪等性キー（例：`source_asset_id + profile + params_digest`）で重複生成を抑制（詳細は #38/#39）

### 10) 容量（Quota）との整合
- 派生生成は一時的に容量を消費する（元を残す場合は恒久的に増える）
- このEpicとして最低限固定すること：
  - 置換を選んだ場合でも `purge_later` の滞留により二重化期間が延び得るため、**後片付け（掃除）戦略**が必要
- 具体の運用ルール（開始前拒否 / 一時超過許容 / 予約方式 など）は **#38/#39 の正本**として確定する

---

## 既存正本（ADR）との整合メモ
- ADR-0014（許可形式/判定方式）：
  - **GIF/APNG許可**に合わせて更新し、MVPの正本として迷いを消す（APNGの判定・扱いを明文化）
- ADR-0002（Asset.kind / 差し替え禁止）：
  - 「最適化＝派生Asset新規作成であり、file差し替えではない」こと
  - 「置換＝参照付け替え＋元ファイルpurge」であること
  を追記して衝突を防ぐ
- ADR-0013（容量・Quota）：
  - 派生生成で容量を食う前提と、拒否/一時超過/掃除の扱いをどこに固定するかを #38/#39 に寄せて正本化する
