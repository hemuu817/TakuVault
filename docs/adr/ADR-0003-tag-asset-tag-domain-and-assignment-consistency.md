# ADR-0003：Tag / AssetTagのドメインモデルと付与整合性契約

## Status

Proposed

## Context

Tag機能では、表記揺れによるTagの重複、異なるUserが所有するAssetとTagの誤関連付け、15件上限を超える競合、一括付与時の部分成功を一貫して扱う必要がある。

本ADRでは、Issue #32を成立させるために必要なTag / AssetTagの同一性、所有権、DB整合性、単体・一括付与、競合、トランザクションおよびライフサイクルの契約を正本化する。

## Decision

### D1. Tagの表示名と同一性判定値を分離する

Tagは、表示用の名称と同一性判定用の値を分けて保持する。

- `tags.name`
  - 利用者へ表示する名称
- `tags.normalized_name`
  - Tagの同一性判定に使用する値
- `tags.user_id`
  - Tagの所有者

`name`、`normalized_name`、`user_id`は必須とする。

Tagの所有権の正本は、ADR-0007に従い`tags.user_id`とする。

別User間では同じTag名を持てる。同一User内で同一Tagと判定された場合は、新しいTagを作成せず既存Tagを再利用する。

既存Tagを再利用しても、後から入力された表記で既存の`name`を上書きしない。最初に作成された表示名を維持する。

### D2. Tag名の正規化規則を固定する

#### 表示名

`name`には、利用者が入力した表記を基本的に保持する。

ただし、表示および入力上の不要な揺れを防ぐため、次の空白整理を行う。

- 前後のUnicode空白を除去する
- 連続するUnicode空白を半角スペース1文字へ集約する
- 大文字・小文字、全角・半角等の表記は保持する

#### 同一性判定値

`normalized_name`には、空白整理後の`name`を基に次の正規化を行った値を保存する。

- Unicode NFKCを適用する
- Unicode case foldingにより大文字・小文字を同一視する
- case folding後に再度Unicode NFKCを適用する
- 前後および連続するUnicode空白を整理する

この規則により、同一User内では、例えば次の表記を同一Tagとして扱う。

- `ＢＧＭ`
- `BGM`
- `bgm`

一方、次の同一視は行わない。

- ひらがなとカタカナ
- 単数形と複数形
- 類義語
- 読み仮名や意味解析による類似語

正規化規則はTag作成と既存Tag探索で共通とし、保存済みの`normalized_name`を読み取りのたびに再計算しない。

正規化規則の変更はTagの同一性を変更するため、既存データの衝突や移行方針を含む別ADRで扱う。

### D3. Tag名は最大50文字とする

- 空文字はTag名として認めない
- `name`と`normalized_name`は、それぞれ1文字以上50文字以下とする
- 同一性判定と上限判定では、すべての正規化を終えた`normalized_name`を必ず確認する
- バイト数ではなく文字数で判定する
- 上限を超えた値を切り詰めて保存しない
- 無効なTag名は422相当で拒否する

DBでも、NULL、空文字、文字数超過および同一User内の重複を拒否する。

### D4. TagとAssetTagのDB整合性を保証する

同一User内のTagの一意性は、`name`ではなく`normalized_name`を基準とする。

DBでは、同一User内で`normalized_name`が重複しないことを保証する。

AssetTagは、少なくとも次の関係を保持する。

- 関連するAsset
- 関連するTag
- AssetとTagに共通するUser

`asset_tags.user_id`はAssetTag独自の所有権の正本ではなく、AssetとTagの所有者一致をDBで保証するための整合性キーとする。

DBでは、次の関係を保証する。

- `asset_tags`のAssetとUserが、実在する同一のAsset所有関係に対応する
- `asset_tags`のTagとUserが、実在する同一のTag所有関係に対応する
- 同一AssetとTagの関連は最大1件とする

これにより、最終的に次の一致を保証する。

```text
asset.user_id == tag.user_id == asset_tag.user_id
```

アプリケーションの認可を迂回した書き込みであっても、異なるUserが所有するAssetとTagを関連付けられないことをDB制約で保証する。

### D5. 1 Assetあたりの付与上限を15 Tagとする

- 1 Assetに関連付けられるTagは最大15件とする
- 上限はAssetに関連付けられているユニークなTag数で判定する
- 同一AssetとTagの重複判定を、15件上限の判定より先に行う
- 重複しているTagは件数を増加させない
- 単体・一括を問わず、Tag数を増加させるすべての経路で同じ上限を適用する
- 競合が発生した場合も、最終的に15件上限を超えないことを保証する

### D6. 単体付与では重複と上限到達を拒否する

1 Assetへ1 Tagを付与する操作を「単体付与」と定義する。

単体付与では、次の結果契約を採用する。

- 付与可能な場合
  - AssetとTagを関連付ける
- 同一Tagが付与済みの場合
  - 422相当で拒否する
  - 重複であることを利用者へ通知する
- Assetが15 Tagに到達済みの場合
  - 422相当で拒否する
  - 上限到達であることを利用者へ通知する

重複または上限到達によって関連付けを作成できない場合、新規Tagを副作用として残さない。

単体付与は意図的な1件操作であるため、重複を成功として黙って処理しない。

### D7. 一括付与は1 Tagを複数Assetへ適用する

一括付与は、1回の操作で1つのTagを複数Assetへ付与する操作とする。

入力されたAsset IDは処理前に重複排除し、以降の件数判定、認可確認および結果集計はユニークなAsset単位で行う。

1回の一括付与で指定できるAssetは、重複排除後で1件以上100件以下とする。

0件または100件を超える場合は処理全体を422相当で拒否し、AssetTagおよび新規Tagを作成しない。

一括付与の対象Tagは、認証済みUserが所有する既存Tag、または認証済みUserのために新たに作成されるTagに限定する。

対象Assetまたは対象Tagに、他Userのレコードや取得不能なレコードが含まれる場合は、処理全体を404相当で拒否する。取得不能だった具体的なIDや所有者情報は外部へ開示しない。

すべての認可と所有者一致を確認する前に、一部のAssetへの書き込みを開始しない。

### D8. 一括付与では対象Asset単位の部分成功を認める

認可と所有者確認を完了した一括付与では、各Assetを次の順序で判定する。

1. 同一Tagがすでに付与されているか
2. 付与済みTag数が15件に到達しているか
3. いずれにも該当しなければ付与可能

結果は次のように扱う。

- 重複
  - そのAssetのみスキップする
- 15件上限到達
  - そのAssetのみスキップする
- 付与可能
  - AssetとTagを関連付ける

重複または上限到達を理由に、一括付与全体を失敗させない。

一括付与結果には、少なくとも次の情報を含める。

- 付与成功件数
- 重複スキップ件数
- 上限到達スキップ件数
- スキップされた各Assetの識別情報
- 各Assetのスキップ理由

件数だけを返し、どのAssetがスキップされたか確認できない結果にはしない。

認可済みの全Assetが重複または上限到達によってスキップされた場合も、200相当の正常な「付与0件」とする。

具体的な結果表示方法はIssue #32で決めるが、最終的にはスキップされた全Assetと理由を利用者が確認できるようにする。

### D9. 競合時も一意性・上限・原子性を維持する

単体・一括を問わず、Tag数を増加させるすべての経路で競合を制御する。

複数Assetを扱う場合は、全経路で共通する一定順序で競合を制御し、処理順の違いによるデッドロックの可能性を下げる。

同一Userが同一の`normalized_name`を持つTagを同時に作成した場合は、最終的に1件のTagへ収束させる。

Tag作成とAssetTag作成は、利用者から見て1つの不可分な操作として扱う。

予期しないDBエラーが発生した場合は、当該操作による部分書き込みを残さない。

一括付与における重複と上限到達は予期されたスキップ結果であり、予期しないDBエラーとは区別する。

付与可能なAssetが0件の場合は、新規Tagを副作用として残さない。

### D10. AssetTagの表示順とライフサイクルを固定する

Assetに付与されたTagは、AssetTagの作成日時が古い順に表示する。同一時刻の場合はAssetTagのIDが小さい順に並べ、表示順を安定させる。

AssetTagを削除した後に同じTagを再付与した場合は、新しい関連として末尾へ表示する。

削除時の契約は次のとおりとする。

- Asset削除
  - 関連AssetTagを削除する
  - Tag自体は削除しない
- Tag削除
  - 関連AssetTagを削除する
  - Asset自体は削除しない
- AssetTag削除
  - Tag自体は削除しない
- AssetTagが0件になったTag
  - 自動削除しない

AssetまたはTag削除時の関連AssetTag削除は、DB側のCASCADEを基本とする。

User削除時のAsset、Session、Tagその他の所有リソース全体のライフサイクルは、本ADRでは決定しない。既存リソースと異なるUser起点のCASCADEをTagだけに導入せず、User削除機能を扱う別IssueまたはADRで横断的に決定する。

## Consequences

- 利用者が最初に入力したTagの表示表記を維持しながら、表記揺れによるTag重複を防止できる
- 大文字・小文字、全角・半角英数字、Unicode空白等は、同一性判定上は同一Tagへ収束する
- NFKCによって互換等価となる文字は、利用者が別の意味で入力した場合でも同一Tagとして扱われる可能性がある
- `normalized_name`をTag同一性の正本とするため、正規化規則を変更する場合は既存データの移行判断が必要になる
- AssetとTagの所有者一致をDBでも保証するため、認可漏れだけに依存せず異なるUser間の関連付けを防止できる
- `asset_tags.user_id`を保持するためデータは重複するが、複合的な所有者一致をDBで保証できる
- 15件上限は複数行をまたぐため、Tag数を増加させるすべての経路で同じ競合制御が必要になる
- 単体付与と一括付与では重複時の結果が異なるため、操作種別ごとの結果契約を維持する必要がある
- 一括付与は部分成功を認めるため、結果サマリと個別スキップ情報が必要になる
- 一括対象を100 Assetに制限することで、1回の同期操作が過大になることを防止する
- 未使用Tagを自動削除しないため、未使用Tagの整理が必要になった場合は後続のTag管理Issueで扱う
- User削除時の全所有リソースのライフサイクルは未決定のまま残る

## Out of Scope

本ADRでは、次の機能・判断を扱わない。

- TagによるAssetの検索・絞り込み
- Tag管理画面
- Tagの改名・統合・手動削除UI
- 複数Tagの同時付与
- Tagの一括削除
- Assetに付与されたTagの全置換
- Tagの色・説明文
- ドラッグ&ドロップによる表示順変更
- 未整理（Usage0）ビューからの一括タグ付与
- User削除時の全所有リソースの削除処理
- migration、model、policy、service、controller、routingの具体的な実装
- 競合制御に使用する具体的なAPI
- レスポンス形式および画面上の具体的な表示方法
- N+1対策およびテストの具体的な実装
