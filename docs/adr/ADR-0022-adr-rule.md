# ADR-0022：ADR運用ルール（正本・記述形式・採用・改訂・置換）

## Status

Accepted on: 2026-10-01

## Context

TakuVaultでは、ADR-0009に基づいて設計判断を記録しているが、文書の増加に伴い、記述形式、採用時の文言、未決定事項、置換関係および参照先の扱いに不統一が生じている。

設計判断の理由と履歴を維持しながら、作成・採用・改訂時の確認を共通化する必要がある。個人開発を前提に、開発者本人が採用を判断し、AIレビューを判断支援として利用する運用とする。

ADR-0009の基本方針を継承しつつ、採用条件・記述要件・改訂時の許容範囲を追加・変更するため、新しい運用ルールとして全面置換する。

本ADRを、ADR本文のテンプレートと利用説明を整備するための正本とする。

## Decision

### D1. ADR・Issue・AGENTS.mdの責務を分ける

- ADRは、採用した設計上のルール・制約・方式・方針と、その採用理由を記録する正本とする。
- Issueは、ADRに従う具体的な作業、受入条件、完了条件、テストケースおよび実装進捗を扱う。
- Issueは関連ADRと該当する決定を参照し、設計判断を独立した別のルールとして再定義しない。
- Issueの受入条件には、ADRへの適合を確認するための観測可能な結果を記載してよい。
- 保証すべき条件や検証の責務分担を設計判断として固定する場合はADRに記録する。具体的なテストファイル、ケース、コマンドはIssueで扱う。
- プロダクトの現在のスコープとIssue snapshotの参照方法は、AGENTS.mdを正本とする。
- 文書間の矛盾を発見した場合は、矛盾する箇所と各文書の責務を確認し、推測で新しいルールを作らない。

### D2. 一つのADRは一つの判断テーマを扱う

- 一つのADRは、一つの重要な判断テーマに限定する。
- 同じ判断を成立させるための複数の契約・制約は、Decision内の小見出しに分けて記録してよい。
- 独立して採用・変更できる別の判断は、別ADRへ分ける。
- 判断に必要な背景、採用理由および影響を残し、作業手順や議論の全記録を本文へ集約しない。
- 補足資料を参照する場合も、何を採用したかと主要な採用理由はADR本文だけで理解できるようにする。

### D3. 判断の優先順位を定める

- 判断が競合する場合は、次の順で検討する。
  1. AGENTS.mdで定めるスコープ・固定条件、および関連する採用済みADRの契約
  2. 実装・テスト・保守を含む運用の単純さ
  3. 将来の拡張余地と置換の容易さ
- 将来の可能性だけを理由に、現在必要な範囲を超える機能や運用を追加しない。
- 既存の採用済み契約を変更する必要がある場合は、変更理由を明示し、本ADRの改訂・置換ルールに従う。

### D4. ステータスは3種類とする

| Status | 意味 | 扱い |
|---|---|---|
| Proposed | 検討・提案中 | 参照してよいが、採用済みの決定として実装の前提にしない |
| Accepted | 採用済み | 採用範囲に含まれる実装・変更は、この決定に従う |
| Superseded | 後継ADRによって置換済み | 判断履歴として保存し、現在の判断は置換先を参照する |

- Statusは設計判断の採用状態を表し、実装完了を意味しない。
- 実装状態と完了判定はIssueで管理し、ADRのAccepted化に関連する実装Issueの完了を要求しない。
- 新規に検討するADRはProposedから開始する。
- Rejectedを含む追加のステータスは導入しない。
- 検討した代替案の不採用理由は、採用するADRの判断理由として必要な範囲で記録する。

### D5. 採用判断は開発者本人が行う

- ADRの採用は、開発者本人の明示的な判断によって決定する。
- codex-connector等のAIレビューは、矛盾、不足、影響および参照関係を確認するための判断支援として利用する。
- AIレビューの指摘がないことや、指摘へ対応したことだけではAcceptedとしない。
- AIレビューで指摘された内容は、採用する契約との関係を確認し、対応要否を判断する。
- 定例レビュー会議、複数人の承認、承認者一覧の記入は必須にしない。
- Accepted化時には採用日を `Accepted on: YYYY-MM-DD` としてStatus節に記録する。
- 採用日は実装完了日や後日の誤字修正日で上書きしない。

### D6. 共通の本文構成と記述方針を使用する

- ADR本文の基本構成は次のとおりとする。

| 項目 | 記載内容 |
|---|---|
| タイトル | ADR番号と判断テーマ |
| Status | 現在の採用状態。採用後は採用日も記録する |
| Context | 問題、制約、既存判断との関係および決定が必要になった背景 |
| Decision | 採用する契約と、その採用理由 |
| Consequences | 利点、受け入れる欠点・制約、運用上の負担 |
| Out of Scope | 本ADRでは決めない事項と、その境界 |
| Related | 関連ADR、Issueの参照先、判断根拠 |

- Contextは簡潔に記述する。固定の行数制限は設けず、判断に必要な情報を残す。
- Decisionは、主語、対象、条件、結果を識別できる文で記述する。
- Decisionを分割する場合は `D1`、`D2` の形式を使用し、Issue等から参照できるようにする。
- 採用理由はContextまたはDecisionに必ず記録する。
- 実際に比較した有力な代替案がある場合は、その不採用理由を記録する。形式を満たすために代替案を作らない。
- Consequencesには、Decisionの再掲だけでなく、採用によって生じる影響を記録する。
- Out of Scopeに特記すべき対象外事項がない場合は、その旨を簡潔に記す。
- 置換関係、確認対象のコミット、具体例、検証方針などの節は、判断の理解に必要な場合に追加する。
- 本文では文書を「本ADR」と呼ぶ。文書全体の採用状態はStatusで示し、「本草案」「採用予定」などの説明を本文へ重複させない。
- 過去の検討経緯を説明する場合は、現在の決定と区別できる表現にする。

### D7. Accepted化前に採用範囲と記述の整合を確認する

- Accepted化前に、次の事項を確認する。
  - 何を採用するかと、その理由が明確である。
  - 採用範囲に必要な判断が確定している。
  - 関連する採用済みADRとの関係が明確である。
  - 本文の表現とStatusが一致している。
  - ADR番号、タイトル、ファイル名および参照先が一致している。
  - 記入用のプレースホルダーや不要な作成説明が残っていない。
  - 置換するADRがある場合は、対象と置換内容が明確である。
- 採用する判断の成立に必要な事項が未確定の場合は、Proposedを維持する。
- 採用範囲から独立した後続判断は、Out of Scope等で境界を明示して分離できる。
- 後続判断が必要な作業は、その判断が確定する前に推測で実装しない。
- 未確定事項を列挙したことだけを、Accepted化の根拠にしない。

### D8. 採用済みの判断と当時の背景を保存する

- Accepted後の決定の変更・撤回・置換は、新ADRで記録する。
- 次の修正は、判断の意味を変えない範囲で既存ADRへ直接行ってよい。
  - 誤字脱字、書式、ADR番号の誤記の修正
  - 同じ参照対象に対するリンク修正
  - 解釈や許容される振る舞いを変えない表現の明確化
- 新しい必須条件、例外、許容範囲または操作契約の追加を、単なる明確化として扱わない。
- 意味が変わるか判断できない場合は、変更前後で許容される振る舞いを比較し、判断を確定してから修正する。
- Contextは、当時の判断背景として保存する。
- 現在の状況と異なることだけを理由に、過去のContextを現在の事情へ書き換えない。
- 修正履歴はGitで追跡する。
- 採用済みADRの参照されている決定番号を、整形だけを理由に変更しない。

### D9. 置換は後継ADRの採用に合わせて行う

- 後継ADRでは、旧ADRから継承する判断と、変更・追加する判断を識別できるようにする。
- 後継ADRのProposed段階では、旧ADRをSupersededにしない。
- 後継ADRの採用に合わせて、次の情報を整合させる。
  - 後継ADRをAcceptedにする。
  - 後継ADRのSupersedesに旧ADRを記載する。
  - 旧ADRをSupersededにする。
  - 旧ADRに、採用された後継ADRへのリンクを追記する。
- 旧ADRのContext、DecisionおよびConsequencesは判断履歴として保存する。修正は、D8で許容する意味を変えない修正に限る。
- 現在の作業が従う参照先は後継ADRへ更新する。過去の判断を示す履歴上の参照は、その意味を維持する。
- 既存の判断と独立した追加判断は、関連する別ADRとして記録できる。新ADRを作成したことだけを理由に既存ADRをSupersededにしない。
- 一部の判断を変更するために旧ADR全体をSupersededにする場合は、維持する判断の参照先も明示する。

### D10. 配置・番号・参照を統一する

- ADRは `docs/adr/` 配下にMarkdownで配置する。
- 新規ADRのファイル名は `ADR-NNNN-<short-name>.md` とする。
- ADR番号は重複させず、使用済みの番号を別の判断へ再利用しない。
- ファイル名、本文タイトルおよび参照元のADR番号を一致させる。
- 関連ADRは、番号とタイトルに加えて実ファイルへのリンクを記載する。
- Issueは `Relates to: ADR-NNNN` とADRへのリンクを記載し、必要に応じてDecisionの節を指定する。
- Issue番号・State・本文の確認は、AGENTS.mdのIssue snapshot参照ルールに従う。
- 現行のIssue参照先は、`automation/issue-snapshot`ブランチの `docs/issues_snapshot.md` と `docs/issues/*.md` とする。
- Issue snapshotを参照できない場合は、古い情報や記憶で補わず、未確認として扱う。
- 外部資料は、どの判断の根拠として使用したか分かる形でリンクする。
- 実装を根拠に判断を記録する場合は、必要に応じて確認対象のコミットやファイルを示す。

### D11. 本文テンプレートと利用説明を整備する

- ADR本文を作成するためのテンプレートを用意する。
- Statusの意味、作成方法、Accepted化時の確認および置換手順を、テンプレートの利用説明として用意する。
- 個々のADRには、そのADRに関する判断を記載する。共通の利用説明を毎回複製しない。
- テンプレートと利用説明は本ADRを参照し、独立した運用ルールを定義しない。
- テンプレートの具体的なファイル配置と作成作業は、整備Issueで扱う。
- 既存ADRの番号修正、リンク修正および参照先整理は、整備Issueで対象を明示する。
- 過去のADRへ新しい形式や採用日を一律に遡及適用しない。確認できない過去の採用日は推測で記入しない。

### D12. ADR-0009を全面的に置き換える

- 本ADRの採用により、ADR運用ルールの正本をADR-0009から本ADRへ移す。
- ADR-0009から次の判断を継承する。
  - 設計判断はADR、具体的な作業と受入条件はIssueで扱う責務分担
  - 1テーマ1ADR
  - 固定条件、運用の単純さ、将来の拡張余地を順に重視する判断方針
  - Proposed／Accepted／Supersededの3種類のStatus
  - 意味を変える変更は新ADRで記録し、意味を変えない修正は既存ADRへ直接行う方針
  - 旧ADRを判断履歴として保存する方針
- 次の記述要件・参照方法を変更する。
  - Contextの「1〜5行」という制限を撤廃し、簡潔さと判断に必要な情報の両立を求める。
  - 新規ADRのファイル名を、番号と短い名称を含む形式に統一する。
  - Issueの参照方法を、現行AGENTS.mdが定めるIssue snapshot運用に合わせる。
  - 判断時の固定条件を、現在のAGENTS.mdと関連する採用済みADRに基づいて確認する。
- 次の運用・記述要件を追加または具体化する。
  - 開発者本人による採用判断とAIレビューの役割
  - 採用状態と実装進捗の区別、および採用日の記録
  - Out of Scopeを含む本文構成、採用理由の記録、Decisionの節番号
  - Accepted化前の確認と、独立した後続判断を分離する条件
  - 意味を変えない修正の許容範囲と、当時のContextの保存
  - 後継ADRの採用、旧ADRのSuperseded化および参照更新の手順
  - 本文テンプレートと利用説明の整備
- ADR-0009のSuperseded化と後継参照の追加はD9に従う。
- 他のADRが定めるアプリケーションの設計判断は、本ADRによって変更しない。

## Consequences

- ADRの作成・採用・置換を共通の手順で扱える。
- 採用状態と実装進捗を区別できる。
- 判断と採用理由を残すことで、将来の再検討時に当時の制約を確認できる。
- 個人開発に必要な範囲で運用を統一し、採用判断の責任を明確にできる。
- 意味を変える変更には新ADRが必要になるため、文書数と参照更新作業は増える。
- 本文テンプレートと利用説明を、本ADRに合わせて維持する必要がある。
- 意味を変えない修正を許容するため、修正が新しい判断を含んでいないか確認する必要がある。
- 過去のADRは当時の記録として残るため、旧形式の文書と新形式の文書が併存する。

## Out of Scope

- アプリケーションの機能・DB・UI・テスト構成に関する設計変更
- 既存の個別ADRの決定内容の変更
- 全ADRの一括書き直し
- 全文書への採用日の遡及入力
- Rejected等の追加ステータス
- 複数人による承認制度や定例レビュー会議
- ADR専用ツール、CI検査、自動採番の導入
- Issue snapshotの生成方式や更新頻度の変更
