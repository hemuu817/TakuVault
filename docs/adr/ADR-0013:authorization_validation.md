# ADR-0013：容量・上限の定義と算定ルール（Quota）※50MB/500MB版

## ステータス
Accepted

## 背景 / 課題
- 添付のサイズ・総容量・1回あたり件数はDB制約だけでは表現できないため、アプリ層での拒否が必要。
- 総容量は同時アップロードで競合しやすく、仕様が曖昧だと簡単に上限を突破する（＝運用で破綻する）。

## 決定（固定値 / bytesで定義）
- 1ファイル最大：**50MB**（`MAX_FILE_BYTES = 50 * 1000 * 1000`）
- ユーザー総容量：**500MB / ユーザー**（`MAX_TOTAL_BYTES = 500 * 1000 * 1000`）
- 1回のアップロード（1リクエスト）最大：**10ファイル**

> 注：本ADRにおける MB は **10進MB（1MB=1,000,000 bytes）** として定義する。

## 定義（総容量の算定対象）
- 総容量（500MB）は、**ユーザーが所有する Asset に “現在 attach されている” Blob** の `byte_size` 合計を指す。
  - 具体的には **ActiveStorage::Attachment 経由で到達できる Blob** の合計（「Attachmentが存在しない孤児Blob」は算定対象外）。
- MVPでは共有・重複所有は扱わない（所有者＝ユーザー）。

> 補足：孤児BlobのクリーンアップはMVP外（将来Issue）。本ADRは「算定対象外」として仕様を固定する。

## 算定タイミング（受付時のゲート）
- 新規アップロード受付時点で、以下を満たさない場合は拒否する：
  - `current_total_bytes + incoming_total_bytes <= MAX_TOTAL_BYTES`
- `incoming_total_bytes` は **同一リクエスト内の全ファイルの合計サイズ**とする。

## 1リクエストの原子性（all-or-nothing）
- **all-or-nothing**：同一リクエスト内のファイル群は「全て許可」または「全て拒否」とする。
  - いずれかのファイルが (a) 50MB超過、(b) 形式不正、(c) 総容量超過、(d) 件数超過 に該当する場合、**そのリクエスト全体を拒否**する。

## 競合（同時アップロード）の扱い（要件）
- 総容量判定は競合し得るため、MVPでは以下を要件として固定する：
  - 判定時に **ユーザー単位で排他** を取る（DBロック）。
  - ロック対象は **usersテーブルの当該ユーザー行** とする（`SELECT ... FOR UPDATE` 等）。
- 万一、処理途中で不整合が起きた場合は「上限を超える状態を残さない」ことを優先し、失敗として扱う。

> 実装方法（サービス層の構成、トランザクション範囲等）は Phase 0 の Asset 側 Issue で確定する。  
> ただし「ユーザー行ロックを前提にする」ことは本ADRで固定する。

## 受け入れ条件（Yes/No）
- [ ] 50MB/500MB/10ファイルが bytes で定義されている（10進MB）
- [ ] 総容量の算定対象が「Attachment経由のBlob合計」で明記されている（孤児Blobは算定対象外）
- [ ] 1リクエストは all-or-nothing と明記されている
- [ ] 同時アップロードはユーザー行ロックで排他する、と明記されている
