# ADR-0004：素材一覧のRole / Tag絞り込みとURL状態・入力検証契約

## Status

Proposed

過去の決定事項を整理した草案。

「補足提案」と記載した事項、および末尾の「Accepted前の確認事項」は未確定とする。

## Context

ADR-0019により、素材一覧とSession画面は、それぞれAsset起点とSession起点の独立した主要画面として分離された。
素材一覧では、UsageのRoleとAssetに付与されたTagを組み合わせ、検索条件を維持しながらAssetを絞り込む必要がある。
本ADRでは、絞り込みの意味、URL状態、入力検証、認可境界および結果表示の契約を定義する。
Tagのドメインモデル・付与整合性およびTag管理操作は、それぞれのADRを正本とする。

## Decision

### D1. 対象は独立した素材一覧とする

- 対象画面は`Assets#index`とする。
- 絞り込みの対象および結果の返却単位はAssetとする。
- Session / Scene画面には、本ADRのRole / Tag絞り込みUIを追加しない。
- `session_id / scene_id`による素材一覧のスコープ指定を扱わない。
- Scene遅延ロード、Where usedツリーとの表示同期を前提としない。
- `Asset.kind`は本ADRの絞り込み条件に使用しない。
- Asset.kindからUsage.roleを推定して絞り込まない。

### D2. RoleはUsageに基づく複数選択条件とする

- RoleはAsset自身の属性ではなく、Usageの`role`を参照する。
- 選択可能なRoleは、現在の次の7種類とする。
  - `background`
  - `standing`
  - `cutin`
  - `panel`
  - `bgm`
  - `sound_effect`
  - `other`
- 初期状態は、`other`を含む全Role選択とする。
- 複数Roleの組み合わせはORとする。
- Roleをすべて解除した場合は、正常な絞り込み状態としてAssetを0件表示する。
- 全Role選択時は、Roleによる絞り込みなしと同じ結果とする。

**補足提案：全選択とUsage存在条件の関係**

過去の「選択RoleのUsageが存在するAssetを対象とする」と「全選択は絞り込みなし」を両立させるため、次の分岐を採用する。

| 選択状態 | Role条件 |
|---|---|
| 全Role選択 | Role条件を適用しない。Usageが0件のAssetも対象に含む |
| 一部Role選択 | 選択Roleのいずれかを持つUsageが1件以上存在するAssetを対象とする |
| 全Role解除 | Assetを0件とする |

- 全Role選択時も、検索`q`およびTag条件は適用する。
- 一部Role選択時は、Session / Sceneを指定せず、認可されたUsageを対象として存在を判定する。
- Usageが0件のAssetを、`other`のUsageを持つAssetとして扱わない。

### D3. 複数TagはAND条件とする

- Tagは複数選択可能とする。
- 選択されたTagをすべて持つAssetのみを対象とする。
- Tag未選択時は、Tag条件を適用しない。
- 同時に選択できるTagは最大15件とする。
- TagのOR検索は扱わない。

選択上限15件は、本ADRにおける検索条件の上限である。
ADR-0003の「1 AssetへのTag付与上限15件」とは別の契約であり、Userが所有できるTag総数を制限しない。

### D4. 検索・Role・Tag条件をANDで合成する

- 最終的なAsset集合は、認可されたAsset集合に対して次の条件を適用する。

```text
検索qの条件
AND
D2で定義したRole条件
AND
D3で定義したTag条件
```

- 検索`q`が利用可能な場合は、Role / Tag条件と組み合わせる。
- `q`、Role、Tagのいずれかを変更しても、他の有効な条件を維持する。
- 検索`q`の対象項目、文字列の正規化、検索演算および入力制限は、本ADRで再定義しない。
- Role / Tag絞り込みの実装を理由として、検索`q`の仕様を変更しない。
- UsageやAssetTagの複数行に一致しても、同じAssetを重複表示しない。
- SQL、JOIN、EXISTS、GROUP BY等の具体的な実現方式は固定しない。

### D5. 絞り込み状態をGET queryで保持する

- RoleおよびTagの選択状態はGET queryで表現する。
- 検索`q`が利用可能な場合は、同じURL状態として保持する。
- リロード後も、URLから選択状態と検索結果を再構築できるようにする。
- Tag未選択時は、`tag_ids`をURLから除去する。
- 絞り込み条件を変更した場合、paginationが存在する画面では1ページ目へ戻す。
- `kind / session_id / scene_id`を本ADRの絞り込み状態に含めない。

**補足提案：初期状態と全解除の区別**

- Role指定のない初回アクセスは、全Role選択として扱う。
- 利用者による全Role解除は、初期状態と区別可能なURL状態として表現する。
- 明示的な全解除を、パラメータ省略による初期状態へ読み替えない。
- 全解除後のリロードでも、全解除状態と0件表示を維持する。

複数Roleと全解除の具体的なquery形式は、Accepted前に確定する。

### D6. 指定Tagをすべて認可範囲内で解決する

- Tag候補および指定Tagの解決は、現在Userの`policy_scope(Tag)`を起点とする。
- 指定されたTagは、すべて現在Userの認可範囲内で解決できることを要求する。
- 次のTagが1件でも含まれる場合は、検索条件全体を422として拒否する。
  - 存在しないTag
  - 削除済みTag
  - 他User所有Tag
  - その他、現在Userが利用できないTag
- 有効Tagと取得不能Tagが混在していても、取得不能Tagだけを除外して検索しない。
- すべて取得不能だった場合も、Tag未選択へ読み替えない。
- 取得不能の理由や所有者情報を、利用者へ区別して返さない。
- 理由の判別を目的として、認可範囲外のTagを取得しない。

**補足提案：入力形式・重複・上限の検証**

- Tag IDの形式を検証したうえで、重複排除する。
- 同じTag IDの重複指定は、1つの選択条件として扱う。
- 選択上限は、重複排除後のTag数で判定する。
- 15件を超える指定は、サーバー側でも422として拒否する。
- 不正値を別の有効IDへ変換したり、不正値を黙って除外したりしない。
- 不正なRole値も、黙って除外して有効な条件として検索しない。
- Role全解除によって結果が0件と決まる場合も、指定Tagの検証を省略しない。

空値、許容するパラメータ構造、Role不正時のHTTP statusは、Accepted前に確定する。

### D7. 正常な0件と検索条件エラーを区別する

正常な絞り込みで一致するAssetがない場合は、通常の検索結果0件として扱う。
Role全解除による0件も、この正常状態に含める。

指定Tagの検証が失敗した場合は、次のように扱う。

- HTTP statusを422とする。
- Asset検索を実行しない。
- 結果領域にはAssetを表示しない。
- 通常の検索結果0件と区別して、検索条件のエラーを表示する。
- 取得不能なTagの存在・所有者を判別できる文言を表示しない。

**補足提案：エラー状態からの復帰**

- 利用者の明示操作でTag条件を解除し、再検索できる導線を設ける。
- Tag条件の解除では、有効な`q`とRole状態を維持する。
- 取得不能Tagが選択候補に存在しなくても、復帰操作を可能にする。
- エラー表示だけを理由として、自動でTag条件を除去して検索し直さない。

### D8. AssetとUsageの認可境界を維持する

- Asset結果の取得は、`policy_scope(Asset)`を起点とする。
- Tag候補に、他User所有Tagを含めない。
- Role判定で参照するUsageも、ADR-0007の所有権境界に従う。
- 全Role選択、Tag未選択、検索`q`なしの場合も、Assetの認可を省略しない。
- 所有権の正本と混在禁止は、ADR-0007に従う。
- Asset参照URLは、認可済みAssetからのみ生成する。

**補足提案：ADR-0007の404との適用関係**

- 本ADRの422は、`Assets#index`に指定された検索条件の検証失敗に限定する。
- リソース自体の取得・更新・削除における認可範囲外の扱いへ、422を拡張しない。
- 所有権境界および`policy_scope`起点の取得方針は変更しない。

ADR-0007には「スコープ外は404」とあるため、この適用関係の正本化と改訂方法は、Accepted前に整理する。

### D9. RoleとTagを同じ絞り込み領域へ配置する

- RoleとTagは、素材一覧上の同じ絞り込み領域に配置する。
- Roleは現在の7種類すべてを常時表示する。
- Tagは登録順で最大7件を常時表示する。
- 8件目以降のTagも、追加の展開UIから確認・選択できるようにする。
- 展開UIの具体方式は、modal / popover / dropdown等のいずれにも固定しない。
- 表示上限7件と、選択上限15件を区別する。
- Role / Tagの選択状態を視覚的に判別できるようにする。
- 常時表示する項目の固定・入れ替え・並び替え設定は実装しない。

**補足提案：順序と非表示の選択状態**

- RoleはADR-0016の用途表示順に揃える。
- Tagの登録順は、`tags.created_at ASC`、同値の場合は`tags.id ASC`とする。
- この順序を、Assetに付与されたTagの表示順とは区別する。
- 展開UIを閉じても、8件目以降に選択中のTagがあることを判別できるようにする。
- 件数表示、選択内容の要約等の具体的な表示方法は実装Issueで決定する。

### D10. Tag付与・Tag管理との責務を分離する

- Tag / AssetTagの同一性、所有権、DB整合性、付与上限および付与操作は、ADR-0003を正本とする。
- 本ADRは、Tagの作成・改名・削除・Assetからの一括解除・未使用Tag管理を扱わない。
- Tag管理操作の成功後に背景の素材一覧や選択条件を更新する契約は、Tag管理側で定義する。
- 古いURL等に取得不能Tagが残った状態で検索要求を受けた場合は、D6に従う。

**補足提案：Tag削除後の条件更新との区別**

利用者によるTag削除の成功後に、Tag管理側が選択条件を更新することと、検索時に取得不能Tagを自動除外することを区別する。
後者は本ADRで認めない。

### D11. 具体的な実装・検証はIssueへ委譲する

次の事項は実装Issueで決定する。

- Controller、Query Object、Serviceの構成
- SQL方式、関連取得方法、indexの必要性
- HTML、CSS、Stimulus、Turboの構成
- 展開UIの方式
- エラーおよび0件状態の最終文言
- テストケースと検証手順
- 検索機能・paginationとの実装順および統合確認

テストの責務分担はADR-0020に従う。
検索・paginationが未実装の場合に、どこまでを当該Issueの完了条件とするかは、実装Issueに明記する。

## Consequences

- 素材一覧をAsset起点で維持しながら、用途とTagの双方で絞り込める。
- RoleとTagを同じ領域で扱い、URLと条件合成を共通化できる。
- RoleはOR、TagはANDであるため、同じ複数選択UIでも検索上の意味は異なる。
- Role全解除は0件、Tag未選択は条件なしとなるため、両者の扱いを実装で混同しない必要がある。
- 全Role選択を条件なしとする補足提案を採用した場合、アップロード直後のUsageなしAssetも初期一覧へ表示できる。
- 同提案では、最後の未選択Roleを選択した時点で、UsageなしAssetも検索対象へ加わる。
- 取得不能Tagを黙って除外しないため、指定されたAND条件が意図せず弱まらない。
- 削除済みTagを含む古いURLは422となるため、条件を解除して復帰する導線が必要になる。
- URLで初期状態と全解除を区別する必要がある。
- Tag候補が増えても常時表示領域を制限できる一方、展開先の選択状態を把握できる表示が必要になる。
- Tag管理を分離することで、絞り込み機能に更新操作の責務を混在させずに済む。

## Out of Scope

- Session / Sceneによる素材一覧のスコープ指定
- Session / Scene画面へのRole / Tag絞り込みUI追加
- Scene遅延ロード、Where usedツリーとの同期
- Asset.kindによる絞り込み
- 検索`q`自体の仕様策定
- ソート仕様、pagination自体の導入仕様
- TagのOR検索
- Tagの作成・付与・解除・改名・削除・統合
- Tag管理画面
- 常時表示項目のユーザーカスタマイズ
- ドラッグ&ドロップによる並び替え
- 絞り込み条件の保存・プリセット
- 具体的なSQL方式や画面更新方式の固定

## Accepted前の確認事項

1. **全Role選択時のUsageなしAsset**
   - D2の補足提案を採用し、全選択時には含めるか。

2. **URLと入力の形式**
   - 複数Roleと明示的な全解除のquery形式。
   - 空値、重複、不正な型、未知のRole値の扱い。
   - Role不正時のHTTP status。

3. **Tag入力の検証**
   - 重複排除後の15件上限をサーバー側でも適用し、超過時422とするか。
   - Role全解除時もTag検証を行うか。

4. **ADR-0007との適用関係**
   - 検索条件検証の422と、リソース取得・操作の404の境界。
   - ADR-0009に従った既存ADRの改訂方法。

5. **UIの補足契約**
   - 422からTag条件を解除して復帰する導線。
   - Tag登録順の同値時の順序。
   - 展開UIを閉じた状態での追加選択Tagの表示。

6. **ADR番号**
   - Tag管理ADR等との重複を確認し、正式番号を付与する。
