# ADR-0021：素材一覧のRole / Tag絞り込みとURL状態・入力検証契約

## Status

Accepted

## Context

ADR-0019により、素材一覧とSession画面は、それぞれAsset起点とSession起点の独立した主要画面として分離された。

Post-MVPの素材探索機能として、UsageのRoleとAssetに付与されたTagによる絞り込みを提供する。URLから選択状態を再現でき、不正な条件によって検索範囲が意図せず広がらない契約が必要である。

本ADRでは、条件合成、URL状態、入力検証、認可境界およびエラーからの復帰方法を正本化する。検索契約と検索条件UIの表示・操作契約を分け、UIの配置や操作方式を変更しても検索条件の意味を再定義しない。

## Decision

### D1. 対象は独立した素材一覧とする

- 対象画面はAssets#indexとする。
- 絞り込みの対象および結果の返却単位はAssetとする。
- Role / Tag条件の意味、検索qとの合成、入力検証、認可およびURL表現は、モーダル等の表示形式に依存しない共通契約とする。
- 検索条件UIは共通契約に従って条件を編集・送信し、検索結果または条件エラーを表示する。UIごとに検索契約を複製・再定義しない。
- 表示・操作契約の担当範囲と未確定事項はD12、具体的な実装への委譲範囲はD14で定義する。
- Session / Scene画面には、本ADRのRole / Tag絞り込みUIを追加しない。
- kind / session_id / scene_idを本ADRの絞り込み条件に含めない。
- Scene遅延ロードやWhere usedツリーとの表示同期を前提としない。
- Asset.kindからUsage.roleを推定して絞り込まない。
- 本ADRの対象外とする機能を、プロダクト全体で廃止する意味には解釈しない。

### D2. RoleはUsageに基づく複数選択条件とする

RoleはAsset自身の属性ではなく、認可されたUsageのroleを参照する。

選択可能なRoleは次の7種類とする。

- background
- standing
- cutin
- panel
- bgm
- sound_effect
- other

初期状態は全Role選択とし、検索時に検証済みのRole集合に応じて次の条件を適用する。UI内の編集だけで検索を実行することは、この条件定義からは要求しない。

| 選択状態 | Role条件 |
|---|---|
| 全Role選択 | Role条件を適用しない。Usageが0件のAssetも含める |
| 一部Role選択 | 選択Roleのいずれかを持つ認可済みUsageが1件以上存在するAssetを対象とする |
| 全Role解除 | 正常な絞り込み状態としてAssetを0件とする |

- 一部Role選択の組み合わせはORとする。
- 一部Role選択では、Session / Sceneを指定せずにUsageの存在を判定する。
- Usageが0件のAssetを、otherのUsageを持つAssetとして扱わない。
- 全Role選択時も、検索qとTag条件は適用する。
- 全選択の判定は、検証・重複排除後のRole集合と許容Role集合の一致によって行う。
- Roleを追加する場合は、既存URLの解釈と全選択判定への影響を含めて設計変更として扱う。

### D3. 複数TagはAND条件とする

- Tagは複数選択可能とする。
- 選択されたTagをすべて持つAssetのみを対象とする。
- Tag未選択時は、Tag条件を適用しない。
- 同時に選択できるTagは、重複排除後で最大15件とする。
- TagのOR検索は扱わない。

選択上限15件は検索条件の上限である。ADR-0003の「1 AssetへのTag付与上限15件」とは別の契約であり、Userが所有できるTag総数を制限しない。

### D4. 検索・Role・Tag条件をANDで合成する

認可されたAsset集合に対して、次の条件を適用する。

```text
検索qの条件
AND
D2で定義したRole条件
AND
D3で定義したTag条件
```

- q、Role、Tagのいずれかを変更して検索する場合も、他の有効な条件を維持する。
- 同じ検索条件を送信した場合は、入力したUIの配置・表示形式にかかわらず、同じ条件合成・検証・認可を適用する。
- UsageやAssetTagの複数行に一致しても、同じAssetを重複表示しない。
- 検索qの対象項目、正規化、検索演算および入力制限は、本ADRで再定義しない。
- 本ADRの422契約を理由として、検索q側の契約を変更しない。
- SQL、JOIN、EXISTS、GROUP BY等の具体的な実現方式は固定しない。

### D5. 検索条件をGET queryで保持し、UIの編集中条件と区別する

#### 状態の区別

| 状態 | 意味 |
|---|---|
| 編集中条件 | UI内で編集している、まだ検索要求として送信していない条件 |
| 送信条件 | GET queryでサーバーへ渡した条件。検証前や不正な条件も含み得る |
| 結果に適用された条件 | 検証に成功し、表示中の検索結果を取得するために使用した条件 |

- 送信条件はサーバー側で検証する。URLに存在することだけをもって、有効な条件や結果に適用された条件とはみなさない。
- 検索qの正規化等は検索q側の契約に従う。入力された文字列と結果に適用された条件が常に同一であるとは仮定しない。
- 未送信の編集を、表示中の結果に適用済みの条件として扱わない。
- 編集から送信への契機、URL更新のタイミング、編集中条件の保持・破棄はD12の操作契約で定義する。即時検索と適用ボタン方式のいずれも、本節では選択しない。

#### パラメータ

Role / Tagの状態には、次のパラメータを使用する。

| パラメータ | 形式 | 意味 |
|---|---|---|
| roles_specified | 文字列"1" | Role選択を明示的に指定していることを表す |
| roles[] | Role名の配列 | 選択したRole |
| tag_ids[] | Tag IDの配列 | 選択したTag |

#### Role状態の解釈

- roles_specifiedとrolesの両方がない場合は、初期状態の全Role選択とする。
- roles_specified=1があり、rolesがない場合は、明示的な全Role解除とする。
- roles_specified=1と有効なroles[]がある場合は、そのRole集合を選択状態とする。
- rolesだけがあり、roles_specified=1がない場合は422とする。
- roles_specifiedに"1"以外の値や配列・オブジェクトが指定された場合は422とする。

#### URL例

| 状態 | URL例 |
|---|---|
| 初期状態・全Role選択 | `/assets` |
| BGMと効果音を選択 | `/assets?roles_specified=1&roles[]=bgm&roles[]=sound_effect` |
| 全Role解除 | `/assets?roles_specified=1` |
| Tagを2件選択 | `/assets?tag_ids[]=12&tag_ids[]=34` |
| RoleとTagを組み合わせる | `/assets?roles_specified=1&roles[]=bgm&tag_ids[]=12` |

#### URL生成と復元

- 全Role選択のURLを生成する場合、Role関連パラメータを省略する。
- 許容Roleをすべて明示した有効な入力も、全Role選択として受け入れる。
- 一部Role選択のURLには、roles_specified=1と選択Role配列を含める。
- 全Role解除のURLには、roles_specified=1だけを含める。
- Tag未選択時は、tag_idsをURLから除去する。
- 空の選択を、roles[]=やtag_ids[]=で表現しない。
- Roleの配列順は検索結果の意味に影響させない。URL生成時はADR-0016の用途表示順に揃える。
- Tag IDの配列順は検索結果の意味に影響させない。URL生成時はIDの数値昇順に揃える。
- 検索qがある場合は、同じURLに保持する。
- paginationがある場合、変更した条件で検索する際は1ページ目へ戻し、ページ移動時は条件を維持する。未送信の編集だけでページを変更しない。
- リロードやURLへの直接アクセスでも、URLの条件を再解釈・再検証し、有効なら同じ選択状態を再構築する。不正ならD8・D9に従い、正常な選択状態へ読み替えない。

URLが保持するのは検索要求の条件であり、未送信の編集内容やデータ変更前の結果集合ではない。再取得時は、その時点の認可範囲・データで条件を検証し、有効な場合に検索する。削除済みTagを含むURLが条件エラーになる場合もある。

### D6. 入力の構造・値・件数をサーバー側で検証する

本節の検証は、リクエストのパラメータ解析に成功した後に行う。

#### Role

- rolesが存在する場合、文字列を要素とする一次元配列を要求する。
- 配列以外の値、ネストした配列・オブジェクト、空文字、未知のRoleは422とする。
- 大文字・小文字の変換や前後空白の除去によって、不正なRoleを有効値へ読み替えない。
- 同じRoleの重複指定は、検証後に重複排除する。
- 解析後の空配列は、roles_specified=1がある場合に限り全Role解除として扱う。
- アプリケーションが生成する全解除URLでは、rolesを省略する。

#### Tag ID

- tag_idsが存在する場合、文字列を要素とする一次元配列を要求する。
- 各IDは、先頭ゼロのない正の10進整数表記とする。
- 空文字、0、負数、符号付き表記、小数、空白付き表記、数値以外、配列・オブジェクトの要素は422とする。
- IDはDBの主キー型で表現できる範囲内であることを要求する。範囲外は422とする。
- 不正な値を整数変換によって別の有効IDへ読み替えない。
- 形式検証後に重複排除し、その後に15件上限を判定する。
- 重複排除後に15件を超える場合は422とする。
- 解析後の空配列はTag未選択として扱う。
- アプリケーションが生成するTag未選択のURLでは、tag_idsを省略する。

#### 共通方針

- 不正な値だけを黙って取り除き、残った条件で検索しない。
- Role全解除で結果が0件と決まる場合も、指定Tagの検証を省略しない。
- Role / Tagの検証がすべて成功するまで、結果Assetの検索を実行しない。
- 認証、認可および検証に必要な照会は、結果Assetの検索とは区別する。

### D7. 指定Tagを認可範囲内だけで解決する

- Tag候補と指定Tagの解決は、現在Userのpolicy_scope(Tag)を起点とする。
- 指定Tagは、すべて現在Userの認可範囲内で解決できることを要求する。
- 次のTagが1件でも含まれる場合は、検索条件全体を422として拒否する。
  - 存在しないTag
  - 削除済みTag
  - 他User所有Tag
  - その他、現在Userが利用できないTag
- 有効Tagと取得不能Tagが混在していても、取得不能Tagだけを除外しない。
- すべて取得不能だった場合も、Tag未選択へ読み替えない。
- 取得不能の理由を判別するために、認可範囲外のTagを取得しない。
- 不存在・削除済み・他User所有を、HTTP status、エラー文言、レスポンス項目等で区別しない。
- 取得不能だった具体的なIDや所有者情報を、エラー情報として返さない。

422というstatusだけで情報漏えい防止が成立するとはみなさない。認可範囲内だけで解決することと、取得不能理由によって応答を分けないことを合わせて守る。

### D8. 検索条件の422と、解析エラーの400・リソース取得の404を区別する

本ADRが定義するRole / Tag検索条件の検証失敗は422とする。

| ケース | HTTP status |
|---|---|
| 解析済みパラメータに、Role / Tagの構造・値・件数違反がある | 422 |
| 検索条件に取得不能Tagが含まれる | 422 |
| 正常な絞り込みで結果が0件になる | 200 |
| リクエストをパラメータへ解析できない | 400 |
| 取得・更新・削除の対象リソースが認可範囲外となる | 既存ADRに従い404 |

- Railsのパラメータ解析エラーを、一律に422へ変換しない。
- 認証失敗、ルーティング失敗、予期しないサーバーエラーを本ADRの422へ変換しない。
- Tag付与・解除・管理等の更新操作へ、本ADRの422契約を拡張しない。
- ADR-0003のTag付与操作における404契約を維持する。

#### ADR-0007との適用境界

取得・更新・削除の対象リソースを認可範囲内で取得できない場合は、ADR-0007に従って404とする。対象リソースは、URLだけでなくリクエスト本文等で指定される場合も含む。

Assets#indexのtag_idsは、Tag自体を取得・操作する対象指定ではなく、Assetコレクションの検索条件として扱う。その条件を認可範囲内で解決できない場合は、本ADRの検索条件検証として422を返す。

Tag解決時もpolicy_scope(Tag)を使用し、ADR-0007の所有権、混在禁止および認可範囲内の取得方針を維持する。

本ADRのAccepted化に合わせ、ADR-0007の適用ルールへ検索条件検証の参照先としてADR-0021を追記し、この境界を明確にする。リソース自体の取得・操作に関する404契約は変更しない。

#### 採用理由

422は、解析できたRole / Tag条件を処理できない場合のアプリケーション契約として採用する。

RFC 9110がGET queryの検証エラーに422を義務付けているという意味ではない。入力検証の一貫性と、取得不能Tagの理由を応答で区別しないことを目的とする。

### D9. 正常な0件と検索条件エラーを区別する

正常な絞り込みで一致するAssetがない場合は、通常の検索結果0件として扱う。Role全解除もこの正常状態に含める。

Role / Tagの検証が失敗した場合は、次のように扱う。

- HTTP statusを422とする。
- 結果Assetの検索を実行しない。
- 結果領域にAssetを表示しない。
- 通常の検索結果0件とは異なる、検索条件のエラーを表示する。
- 取得不能Tagの存在・所有者・削除状態を判別できる情報を表示しない。
- エラー表示だけを理由として、自動で条件を除去して再検索しない。

Role値の不正、Tag ID形式の不正、Tag選択上限超過については、利用者が修正するための説明を表示してよい。ただし、取得不能Tagの理由や具体的なIDを識別する説明は表示しない。

この契約は検索要求に対する検証結果を扱う。未送信の編集に対するUI上の入力補助とは区別し、クライアント側の検証でサーバー側の検証を置き換えない。

422応答を画面へ反映する場合、モーダル内にエラーを表示するだけで背景の結果領域に以前のAssetを残すことは認めない。通信失敗を正常な0件や検索条件の422へ読み替えず、送信中・通信失敗・競合する応答の表示はD12の操作契約で定義する。

### D10. 利用者の明示操作で検索条件エラーから復帰できるようにする

#### Tag条件エラー

- 利用者の操作でTag条件をすべて解除し、再検索できる導線を設ける。
- 有効なRole状態と検索qを維持する。
- 取得不能Tagが選択候補に存在しなくても、解除操作を可能にする。

#### Role条件エラー

- 利用者の操作でRole条件を初期状態の全Role選択へ戻し、再検索できる導線を設ける。
- 有効なTag条件と検索qを維持する。
- 初期化はRole関連パラメータを省略したURLで行う。

#### Role・Tagの双方が不正な場合

- Role / Tagをまとめて初期化する導線を設ける。
- Roleを全選択、Tagを未選択とする。
- 検索qは検索側の契約に従って維持する。

一方のエラーだけを表示したことを理由に、未検証の他方を有効とみなさない。復帰操作後のリクエストでも、すべての入力検証と認可を再実行する。

Role全解除はD2の正常な0件、Role初期化は全Role選択であり、同じ操作として扱わない。Tag条件の解除はTag未選択を意味する。UIの文言・操作契約では、変更する条件と維持する条件を判別できるようにする。

モーダルを閉じることや未送信の編集を取り消すことだけでは、条件エラーからの再検索完了とはみなさない。復帰導線から送信する契機と、送信前後のUI状態はD12で定義する。

### D11. AssetとUsageの認可境界を維持する

- 素材一覧では認証を必要とし、Assets#indexに対する認可を行う。
- 結果Assetの取得はpolicy_scope(Asset)を起点とする。
- Tag候補に他User所有Tagを含めない。
- Role判定用Usageも、ADR-0007に従い、Asset側とSession / Scene側の所有者が現在Userと一致する範囲に限定する。
- 全Role選択、Tag未選択、検索qなしの場合も、認可を省略しない。
- Asset参照URLは、認可済みAssetからのみ生成する。
- クライアント側の選択肢制限を、サーバー側の検証・認可の代わりにしない。

### D12. 検索条件UIの表示・操作契約を検索契約から分離する

検索条件UIはD2〜D11の共通契約を参照する。表示場所をまとめることと、検索q・Role・Tagそれぞれの検索仕様を一つに統合することは区別する。

#### 表示契約

本草案では次の表示契約を維持する。以下の「常時表示」は素材一覧上で展開操作なしに見えることを意味し、閉じたモーダル内への格納を含めない。

- RoleとTagを、素材一覧上の同じ絞り込み領域に配置する。
- Roleは現在の7種類を常時表示する。
- Roleの表示順はADR-0016のUsage::DISPLAY_ROLE_ORDERに揃える。
- Tagはtags.created_at ASC, tags.id ASCの順で、先頭7件までを常時表示する。
- 8件目以降のTagも、展開UIから確認・選択できるようにする。
- 展開UIを閉じても、追加領域に選択中のTagがあることを判別できるようにする。
- Role / Tagの選択状態を視覚的に判別できるようにする。
- 表示上限7件と選択上限15件を区別する。
- 常時表示項目の固定・入れ替え・並び替え設定は実装しない。

Tag候補の登録順と、ADR-0003が定義するAssetに付与されたTagの表示順は区別する。

追加Tagの展開UIと、検索条件全体をまとめるモーダルは区別する。条件全体をモーダルへ移す場合は、上記の常時表示契約も合わせて改訂する。

#### 操作契約の未確定事項

次の事項は、本草案では未確定とする。検索条件UIの実装前に本節で決定するか、決定した操作契約のADRを本節から参照する。具体的なクラス・ブラウザAPI等の選定とは区別する。

- qの配置、追加Tagの展開方式、および検索条件全体をモーダルへまとめるか。
- 条件編集から検索要求を送信する契機。即時検索、適用ボタン、一覧上と展開先の操作をどう揃えるか。
- 閉じる・キャンセル・Esc・背景クリックでの編集中条件の保持または破棄と、再度開いた際の復元元。
- 条件の解除・初期化の対象範囲、qの維持、およびD10のエラー復帰から再検索する操作。
- URLと結果・条件表示を更新するタイミング、ブラウザ履歴への追加または置換、戻る・進む・Turboキャッシュからの復元。
- 送信中、通信失敗、連続操作による応答の競合、および422反映時のモーダル・条件表示・結果領域の状態。D9の結果非表示契約を維持する。
- モーダル採用時のフォーカス移動・復帰とキーボード操作。

編集中条件、送信条件、結果に適用された条件を混同せず、URL・条件表示・結果またはエラーが対応する状態を定義する。ADR-0019のSession切替における履歴・通信失敗の契約を、素材検索へ自動的に適用しない。

追加選択の件数表示・要約方法、文言、HTMLおよびCSSの具体化はD14に従う。

### D13. Tag付与・Tag管理との責務を分離する

- Tag / AssetTagの同一性、所有権、DB整合性、付与上限および付与操作はADR-0003を正本とする。
- 本ADRはTagの作成・付与・解除・改名・削除・未使用Tag管理を実装範囲に含めない。
- Tag管理内の検索条件・一時UI状態と、素材一覧の検索条件は別々に保持する。Tag管理内の検索文字列等を、素材一覧のqやRole / Tag条件へ混入させない。
- Tag管理操作の成功後に、背景の素材一覧や選択条件を更新する契約はTag管理側で定義する。
- 利用者によるTag削除の成功後に選択条件を更新することと、検索時に取得不能Tagを自動除外することを区別する。
- 古いURL等に取得不能Tagが残っていた場合は、D7に従って422とする。

### D14. 実装・検証の具体化はIssueへ委譲する

検索条件の意味・合成・状態反映の契約は本ADRを参照し、IssueやUI側で重複定義しない。D12の適用・キャンセル・URL反映等の操作契約はADRで定義し、次の具体化を実装Issueへ委譲する。

- Controller、Query Object、Serviceの構成
- SQL方式、関連取得方法、indexの必要性
- HTML、CSS、Stimulus、Turboの構成
- 決定済みの操作契約に従う展開UI・選択要約・復帰導線の具体的な表示方法
- エラーおよび0件状態の最終文言
- テストファイルの配置と具体的なケース
- 検索機能・paginationとの実装順および統合確認

テストの責務分担はADR-0020に従う。

- HTTP status、入力検証、認可はサーバー側のテストで保証する。
- JavaScript内部の状態操作は、対応するJavaScriptテストで保証する。
- URL変更から再取得・再表示までの主要導線は、必要な統合テストで保証する。
- 検索条件の合成・検証はUIの表示形式から独立して検証し、条件編集・送信・復元と結果表示の接続は統合テストで確認する。
- モーダル採用時のフォーカス・キー入力等のブラウザ固有挙動は、ADR-0020に従い実ブラウザで保証する。

Tag / AssetTag基盤、検索qおよびpaginationの実装状態は、本ADRの採用状態と区別する。未実装の前提を絞り込み実装へ無断で追加せず、依存関係と完了条件を実装Issueに明記する。

## Consequences

- RoleはOR、TagはANDとして、検索qと組み合わせられる。
- 初期一覧ではUsageなしAssetも表示できる。
- 全Role選択の条件で検索した場合はUsageなしAssetも対象となる。最後のRoleをUIで選択しただけで、結果を即時更新することは要求しない。
- Role全解除は0件、Tag未選択は条件なしとなるため、両者の意味をUIと実装で区別する必要がある。
- 初期状態とRole全解除をURL上で区別できる。
- URLは検索条件を再現するが、データ変更前の結果集合までは保存しない。
- 本ADRのRole / Tag条件の検証エラーは422へ統一されるが、検索q側の契約、解析不能なリクエストの400とリソース操作の404は維持される。
- 取得不能Tagを自動除外しないため、指定したAND条件が意図せず弱まらない。
- 削除済みTagを含む古いURLは422となり、利用者による条件解除が必要になる。
- 不存在・削除済み・他User所有を同じ応答として扱うことで、取得不能理由を応答から区別させない。
- Statusの統一だけでは認可や情報秘匿は成立せず、認可範囲内の取得とエラー内容の制御が必要になる。
- RoleとTagの双方が不正な場合も、明示的な初期化操作によって復帰できる。
- Tag管理の操作責務を、絞り込み機能へ混在させずに済む。
- 検索条件UIを変更しても、検索条件の意味・合成・検証・認可・URL表現を共通契約として維持できる。
- UIの編集中条件と検索へ送信した条件を区別するため、適用・取消・URL反映等の操作契約をD12で具体化する必要がある。

- ソート仕様、pagination自体の導入
